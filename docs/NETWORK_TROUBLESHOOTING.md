# CPA 网络优化与故障排查经验

整理日期：2026-11-01。本文根据匿名历史案例和官方资料整理排查方法，供维护者复用。整理过程没有连接生产 VPS、切换节点、刷新额度或调用模型。历史测量不能代表当前线路状态。

具体实例地址、节点清单、凭据、完整日志和备份位置保存在私有运维记录中。本文与[代理接入与运维](PROXY_OPERATIONS.md)互相补充；诊断源码见[可选传输诊断补丁](../patches/codex-transport-trace/README.md)。

## 先确定实际链路

一个适用于本案例的结构是：

```text
CPA → 本机受鉴权保护的代理入口 → 业务策略组 → 前置节点
    → 固定出口代理 → 模型服务
```

前置的国家、名称与最终出口不同。维护时应分别检查业务策略、实际叶节点和目标可见出口，而不是仅记录自动组名称。

CPA 连接本机代理所用的 HTTP／SOCKS 协议、固定出口代理所用的协议，以及前置的 VLESS／VMess／Hysteria2 协议，位于不同链路段。修改某一段不要求同时修改其它段。[Mihomo 的 dialer-proxy 文档](https://wiki.metacubex.one/en/config/proxies/dialer-proxy/)说明了出站代理经另一代理建立连接的关系；[Webshare 协议说明](https://help.webshare.io/en/articles/8375305-understanding-proxy-connection-types-direct-rotating-and-backbone)列出了其 HTTP／SOCKS5 支持。具体账户和端点仍应按供应商配置核对。

需要按稳定优先级选主备时，可采用按顺序选择可用成员的 fallback；最低延迟选择是另一个目标。行为参考[官方 fallback 说明](https://wiki.metacubex.one/en/config/proxy-groups/fallback/)，升级后应重新验证回切、全部失败与空候选三种情形。保持固定出口还需检查完整路由及出口保护，不能只看组内有没有 DIRECT。

## 统一 Windows 和 VPS 的比较条件

| 需要对齐的条件 | 应记录的内容 |
|---|---|
| 核心和订阅 | 核心版本、完整连接参数及订阅来源版本；同名节点可能参数不同 |
| 请求路径 | 前置单独出站还是完整固定出口链路；系统代理、TUN 或应用显式代理 |
| DNS | 实际解析位置、所用解析器、连接地址族及结果；不要只比较配置名称 |
| 探测 | 同一目标、同一状态码条件、同一采样窗口、冷连接或复用连接 |
| 协议 | 各段的 HTTP／SOCKS5、TLS、ALPN／HTTP 版本，不能把所有变化归为“节点” |
| 统计 | 成功数／总数、失败阶段、成功样本耗时与重试口径 |

系统 ICMP ping、客户端延迟、目标 HTTP 可达、账号额度查询、真实流式生成，应作为不同层次的结果保存。统一延迟测量会处理连接握手带来的差异，见[Mihomo unified-delay 说明](https://wiki.metacubex.one/en/config/general/#unified-delay)；其数值不能直接视为冷建连、首字或完整生成时间。

DNS 变化需要通过受控比较验证效果。一次更低的数值不足以证明链路被修复，也不能凭 Windows 的一次低延迟推定 VPS 的整条出站路径应有相同耗时。

## 分类失败，保留证据层级

| 现象 | 首先核对 | 不能仅据此判定 |
|---|---|---|
| 外层显示限流／请求失败 | 内层错误、目标模型与提供商、认证可用性、冷却状态、最近传输错误 | 一定是账号额度耗尽或机场限速 |
| 延迟正常但模型失败 | 探测与模型调用是否走同一路径；是否有重试和流式读取 | 整条链路已排除问题 |
| TLS EOF 集中在约 5 秒 | 对齐内核拨号、握手、上下文和应用日志，并记录对应版本 | 所有 EOF 同源，或某供应商固定有 5 秒限制 |
| 较长请求发生 HTTP/2 PROTOCOL_ERROR | 握手后最后阶段、响应是否已开始、取消与重置证据 | 节点协议或某一方软件已被确认为唯一根因 |
| 新实例启动后短时模型不可用 | 模型注册和提供商初始化是否完成 | 所有 400 或长期运行故障都是初始化问题 |

匿名历史记录中，一组 49 次带时长的 TLS EOF 有 47 次落在约 5.05–5.18 秒，另有内核 deadline 日志；同一排查还用普通 curl 观察到相似切断。这些证据支持继续定位连接期限相关环节，不能只归因于 CPA 的 TLS 指纹，也不能准确分摊每一段的耗时。该案例未在本次文档整理中重新执行。

健康检查的 timeout 只是该检查的预算，不会自动改变连接器内部可能存在的其它期限。不要根据推测增加未被对应版本支持的配置键。

## 读懂连接阶段日志

可选补丁针对固定 CPA 基线中的一条特定 HTTP/uTLS 路径；它不代表所有提供商和 WebSocket 都已被覆盖。它通过环境变量指定的哨兵文件显式启用，细节见[补丁维护说明](../patches/codex-transport-trace/README.md)。

| 阶段或字段 | 判读要点 |
|---|---|
| trace_attempt、at_utc | 按每次传输尝试和时间关联；一次用户调用可有多次尝试 |
| proxy_dial_start／end | 本机代理很快接受连接，仍可能有后续远端连接等待 |
| tls_start／end | 这一段可能包含代理链后续建连及目标握手，不能全计为加密计算 |
| request_written | 需结合顺序分辨代理 CONNECT 与上游业务请求 |
| first_response_byte／response_headers | 区分握手后的等待和已收到响应头的阶段 |
| first_body_read | 首次读取非空响应字节，不等于模型首个 token 或可见文字 |
| body_end／body_closed | EOF 或关闭可能正常；同时核对上层流式完成事件和调用结果 |
| error_class、context_state | 错误分类与取消状态是线索，不能单独证明责任方或取消发起者 |

私有节点观察器可用时间和本地端口辅助关联，但短连接可能被轮询漏掉，失败拨号也可能没有可用端口。容器网络或节点映射变更后，需要验证观察器使用的映射是否仍有效。

日志只保留必要元数据，控制留存和访问范围。同步写日志有成本；没有受控开关 A/B 就不应声称零性能影响。

## 最小复现与验收

1. 记录失败时间、时区、模型、流式与重试情况，以及脱敏后的外层和内层错误。
2. 先只读检查服务健康、目标模型就绪、策略组选中、叶节点和预期出口。
3. 按最后成功阶段分类，分开统计连接前失败、握手后失败、流读取中断和取消。
4. 先做轻量可达检查。需要真实模型复现时，在获授权的隔离环境固定凭据、模型、请求格式、前置和出口，限制请求数。
5. 一次改变一个因素，例如固定出口同一端点的 HTTP／SOCKS5 包装。记录目标、状态码规则和采样窗口。
6. 同时记录失败数和成功数，保留失败耗时。整体成功率与单次上游尝试成功率分开，不能只报告最快成功样本。

某次目标的无认证 GET 检查曾以 405 作为预期可达结果；它不是所有服务通用的健康码，也不验证账户、配额、请求格式或流式生成。探测预算、间隔和预期状态应随服务与核心版本明确记录，参考[策略组公共字段](https://wiki.metacubex.one/en/config/proxy-groups/)。

匿名案例中的前置 A 可达样本为 6/6，备用 B、C 各为 5/6；另一次保留生产重试的三次模型调用均完成，约 3.8–6.1 秒。这些小样本支持当时的选择，不能视为协议排名、长期成功率或无重试的上游成功率。

## 升级和回退边界

- 连接复用等优化应单独实验；相似上游 issue 或一次成功不足以证明唯一根因。
- 更新前端或统计容器时，保留已部署后端的镜像、运行参数、挂载和诊断开关。
- 更换官方后端可能移除私人诊断补丁，需重新对照源码路径验证覆盖范围。
- 关闭哨兵只影响新开启的追踪；已有请求及独立观察器分别处理。
- 网络配置、后端程序和统计数据库有不同的备份边界。回退前检查后续变更，不恢复旧数据库覆盖新增事件。
- 本仓库不保存生产备份、私有观察器或实例操作脚本；引用仓库内资料和官方来源，不依赖维护者桌面路径。
